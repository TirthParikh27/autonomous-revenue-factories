# Weekly review

You propose. The operator merges or closes. Read `CLAUDE.md` and `budget.yaml` first.

## Inputs

- `journal/<date>/` run reports for the last 7 days, including every "Not done" and "Denied or blocked" section.
- `ledger/spend.jsonl` and `ledger/revenue.jsonl`.
- `state/metrics/` for the last 7 days and `state/items/` histories.
- `escalations/approved/` and `escalations/rejected/` from the last 30 days, with the operator's one-line reasons.
- `state/submissions.jsonl`, including any rejection text the operator recorded.
- `journal/LESSONS.md` and last week's `journal/reviews/` file, including proposals whose review date has arrived.

## Steps

1. Build the funnel table from item histories, not from run report prose: counts entering and leaving each stage this week and to date, kill reasons, and spend per stage from the ledger.
2. Compute: cost per killed idea by stage, cost per demand-validated idea, submissions used this quarter against the cap, verified revenue minus recorded spend for the factory and per live app.
3. Look for these specific problems:
   - Ideas dying late that could have died earlier. A demand-test kill whose cause was visible in the scout file is a gap-mining defect.
   - Specs that passed the gate and were then rejected by the operator at `A-DEM-1` or `A-SUB-1`. The gate is too loose.
   - Run reports claiming an outcome without a read-back or check output.
   - Repeated permission denials or missing tools.
   - Content angles ranked by signups or downloads per published post. Flag any angle with reach and no conversions.
   - Drafts the operator did not publish. That is a signal about quality or load.
   - Operator time per week implied by open packets. More than 5 open packets is a design problem.
   - Any App Review feedback, word for word.
4. Judge last period's proposals whose review date has arrived, against the metric each one named. Say plainly whether it worked.
5. Write at most 3 proposals. Each has: observation with file references, hypothesis, the single change, the metric that will judge it, and the review date. One change per skill per week.
6. Open one pull request per proposal. Allowed paths: `skills/`, `agents/`, `data/seeds.yaml`, `data/content_formats.yaml`, `data/spec_template.md`, new rows in `data/review_checklist.yaml`, additions to `data/excluded_categories.yaml`.
7. Promote at most 3 lessons to `journal/LESSONS.md` in the same pull request as the review file: dated, one or two lines, each linking the evidence. If the file exceeds 80 lines, propose which entries to retire.
8. Write `journal/reviews/<iso-week>.md` with the funnel table, the numbers from step 2, the verdicts from step 4 and links to the pull requests.
9. Post a Slack summary under 80 words with the pull request links.

## Tools

Read, Grep, Glob, Write, Bash for git, the GitHub connector to open pull requests. No web tools and no vendor connectors.

## Deterministic check

CI on each pull request runs a path check that fails if the diff touches `CLAUDE.md`, `ESCALATION.md`, `budget.yaml`, `checks/`, `.github/`, hooks or settings, or removes a line from `data/excluded_categories.yaml` or `data/review_checklist.yaml`. The funnel table is regenerated by `checks/funnel` from item files and must match the one in the review file.

## Outputs

- `journal/reviews/<iso-week>.md`.
- Up to 3 pull requests.
- Lesson entries in `journal/LESSONS.md`.

## Stop conditions

- Fewer than 3 run reports in the week: write the review file with the numbers, make no proposals.
- A needed change is to a protected file, a threshold or a cap: raise `GEN-1` with the evidence. Do not open a pull request for it.
- No evidence for any change: propose nothing. Zero proposals is a valid result.

## Never

- Never loosen a kill threshold, the submission cap, the overlap cap or the copy lint, and never propose doing so in a pull request.
- Never propose more volume (more apps, more posts, more accounts) as a fix for low conversion.
- Never propose a format that uses testimonials, AI people as users, purchased engagement or automated publishing.
- Never judge a change on views, or on fewer than the sample the proposal named.
- Never merge a pull request or edit files on `main`.
- Never state the factory is profitable without subtracting recorded spend.

## Finish

End by calling the shared `run-report` skill. Include the `checks/funnel` output and the pull request URLs.
